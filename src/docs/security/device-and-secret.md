# 设备密钥管理

本章介绍两个概念：设备的管理和密钥的管理。

## 威胁模型

为什么交叉签名和设备验证如此重要？

Matrix 协议有一条重要的设计原则：服务器不可信。您可以这样理解——运营服务器的人可能想要破解您的账号密码、拿到您的聊天记录，再冒充您给别人发消息，而客户端必须尽可能阻止这种事发生。

我们当然承诺 NerChat! 足够安全、您的数据受到保护，也绝不会窃取密码或做非法登录；但我们的承诺本身不能被当作依据——换句话说，服务器和运营方都是不可信的，您完全有理由怀疑我们。这也正是 Matrix 要解决的问题：如何在服务器不可信的前提下，建立起可信的消息通道。

客户端面临的主要威胁有三个。

### 中间人攻击

在双方交换密钥、进行验证的过程中，服务器可以发起中间人攻击。关于[中间人攻击](https://www.jianshu.com/p/9742ece54ded)的资料很多，这里不再展开。

### 假冒登录

服务器可以利用您的密码，在未经授权的情况下登录、创建新设备，并与您的朋友互相发送消息，甚至可以做到不留任何痕迹，连明文密码都不需要知道。

再进一步，服务器还能直接登录一个账号，混进该账号已加入的群组，监听其他人的加密聊天。

### 破解密钥库

如果客户端对密钥库的保护不够严密（例如安全短语与登录密码相同），服务器甚至能解密客户端上的全部加密聊天内容。

针对这三点，一个经过严格验证的 Matrix 聊天网络都可以规避。

- 应对密钥库被破解：强烈建议不要把登录密码和密钥库的安全短语设成同一个。请记住——登录密码对服务器来说是完全不加密的。
- 应对中间人攻击和假冒登录：客户端之间需要互相进行交叉验证、建立签名信任，通过识别签名来确保对话不会被泄露。

服务器当然可以登录您的账号，但只要它无法解密您的 Megolm 密钥库，就无法伪装成您的设备，只能把自己变成一台新设备——而这台设备的公钥绝不会获得信任您的人所给出的交叉签名。

先解释一下原因：为什么服务器不能用您已经公开的公钥来伪装自己？因为它没有对应的私钥——私钥保存在您的 Megolm 密钥库里，服务器拿不到。认证体系的坚固之处正在于此：服务器无法伪装成对方来骗取您朋友的信任。

如果原本安全的聊天中突然出现一台不受信任的设备，您的朋友可以通过其他渠道向您核实，中间人也就无所遁形。如果不方便直接联系您，朋友也可以向这台可疑设备提问，确认它是否真的由您持有——这些细节都会暴露出服务器的动作。

因此，如果您真的不信任 NerChat! 的服务器，请多留意朋友设备的验证状态。当然，如果对方的设备没有您的签名，您的软件也会给出提醒。

## 登录设备管理

客户端可以随时查看自己登录了哪些设备，并下线从未在自己手中登录过的设备。在新设备上登录后，需要提供安全密钥来取回密钥库、解密历史聊天记录，同时也让新设备快速获得信任——密钥库里有其他人对您公钥的签名，这些签名正是信任的来源。如果一台设备拿不到密钥库，它还有一种快速获得信任的方式：取得您的签名。而如果有人用您的密码在未经允许的情况下登录，它既拿不到密钥库、也拿不到签名，自然无法获得其他设备的信任——在其他设备看来，它会显示为红色或灰色，表示不可信任。

您可以随时管理登录设备，把任意一台设备下线、清除它在服务器上的登录状态。这可以当作在不信任的平台上误登录之后的补救措施——这类平台通常都是 Web 端。另外请放心，出于安全策略，Web 端不会把密钥库写入永久存储；虽然会带来一些不便，但您不必担心密钥泄露。

## 恢复备份的密钥库

由于各种原因，设备上的部分密钥可能丢失，导致某些消息记录无法解密。通常一次简单的密钥恢复就能解决：客户端会重新向服务器请求加密的 Megolm 密钥库备份，您提供安全密钥解密后，客户端会把现有密钥库与备份合并，再用相同的密钥重新加密并上传到服务器。这个过程称为“恢复密钥库备份”。

## 从不向未验证的设备发送加密消息

既然没有持有您所信任的交叉验证公钥的设备，都有可能是服务器安排的“间谍”，您当然可以选择拒绝信任任何未验证的用户、不与他们加密通信，客户端里也提供了这个选项。开启后，每个加密聊天建立之前，客户端都会检查对方的交叉验证签名；一旦发现签名不在您的信任范围内，就会先要求您与对方完成交叉验证。

这会给日常使用带来很大不便，而且 NerChat! 已经承诺了服务器的安全性，不会自砸招牌，所以您基本没有必要这么做。如果确实需要与某人交流高度机密的消息，直接验证对方的设备即可，不必对所有聊天对象都严格设限。

如果您仍然想开启，方法如下。
